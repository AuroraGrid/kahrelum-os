Intelligence that has to earn its PASS.

KAHRELUM OS is an application-layer evidence-to-decision control plane for research, forecasting, AI evaluation and decision work. It separates fact from inference, attacks its own conclusions, checks mission completion, and preserves the record instead of rewriting history.

Current formal release · v2.3.3 FINAL

Canonical pipeline

ROUTER → SCOUT → SOURCEGRID → K-ALIGN → IPR
→ BLACKGLASS-I → CRF → COMMAND → BLACKGLASS-II → RECORD LOCK

SCOUT discovers. SOURCEGRID establishes provenance. K-ALIGN tests identity and scope. IPR finds the variables that matter next. BLACKGLASS attacks. CRF prices uncertainty. COMMAND decides. BLACKGLASS-II attacks the action. RECORD LOCK freezes the analytical state.

v2.3.3 core control

MCRI — Mission Contract Release Interlock

Before retrieval, explicit requirements compile into an atomic mission contract. KAHRELUM cannot self-certify PASS while mandatory active requirements are omitted, substituted, unresolved or unsupported. COMMAND cannot override MCRI.

SATISFIED_NEGATIVE requires actual negative closure — “I didn’t find it” is not automatically evidence that it does not exist.

Real case: should v2.3.3 RC1 be promoted?

This is not a toy prompt. The release decision itself is a compact example of the control plane operating on a real mission.

MISSION CONTRACT
Determine whether the frozen v2.3.3-RC1 candidate clears every predeclared Bench v3 promotion gate without changing the candidate during evaluation.

SOURCEGRID
Bind the candidate tree, candidate archive, benchmark master, benchmark lock, clean-room raw run and independent adjudicator to explicit hashes. Do not treat the public docs repository as the candidate artifact.

K-ALIGN
Verify the same 33-file candidate identity before and after the run. Check that benchmark, adjudicator and candidate identities do not drift.

BLACKGLASS-I
Attack for false PASS, dropped mandatory atoms, missing required objects, substitute predicates, denominator/window errors and silent RECORD LOCK rewrites.

CRF / RELEASE GATE
This mission is gate-based rather than a free-form probability call: every frozen threshold must clear. One hard blocker is enough to prevent promotion.

COMMAND
PROMOTION_GATE: PASS after 30/30 VALID_PASS, architecture mean 98.37, mission mean 97.07, zero hard blockers, zero listed escape classes, no candidate hash drift and zero mid-run patches.

BLACKGLASS-II
Do not turn PASS into “perfect.” Preserve V3-04, V3-26 and V3-29 as non-blocking defects and preserve the longer-term validation boundary.

RECORD LOCK
Promote the exact candidate bytes; keep the portable tree and archive hashes immutable; append future doctrine around the release rather than rewriting it.

Claim discipline
